# P45 v2.7.4 PAIR Gate Timing and Transaction PATCH DRAFT

## 0. 문서 지위와 범위

- 상태: `DRAFT_ONLY / NOT_OFFICIAL`
- project version: `P45 v2.7.4`
- 목적: PG05·PG14·final PAIR state의 prediction staging 순환 제거
- 변경 범위: 평가 시점, payload layer, round transaction 순서
- 변경하지 않음: PG01~PG14 연구 predicate와 threshold, state precedence, 50/200, risk/recent/structure/bonus, Pareto, ranking, SET1/SET2, outcome, PRIMARY/SUPPORT, PAIR→CORE
- 코드·DB·WALKFORWARD 변경을 승인하지 않는다.

## 1. 불변 원칙

1. 모든 PG01~PG14와 final pre-result PAIR state는 R outcome 최초 접근 전에 확정한다.
2. R의 모든 연구 입력은 `source_end_round = R-1`까지만 사용한다.
3. PRELOCK, FINAL-PREDICTION, FINALIZATION은 서로 다른 payload/record layer다.
4. 앞 layer의 hash만 뒤 layer가 참조한다. 뒤 layer는 앞 layer hash 계산에 들어가지 않는다.
5. round transaction commit 결과는 gate/state 입력이 아니다.
6. commit 실패 시 전체 round를 rollback하고 COMPLETE로 표시하지 않는다.

## 2. PHASE 1 — PRELOCK

### 2.1 역할

PRELOCK은 outcome 접근 전 R-1 경계, 후보, rule signature 및 pre-result 원시 입력 묶음을 잠그는 prediction integrity layer다. PG05·PG14 결과와 final PAIR state를 포함하지 않는다.

### 2.2 canonical PRELOCK payload

```json
{
  "candidate_bundle_hash": "<sha256>",
  "data_prefix_hash": "<sha256>",
  "evaluation_round": 1,
  "outcome_access_count_before_prelock": 0,
  "policy_linkage_hash": "<sha256>",
  "pre_result_raw_input_bundle_hash": "<sha256>",
  "prelock_version": "PAIR-PRELOCK-1.0",
  "rule_signature_bundle_hash": "<sha256>",
  "source_end_round": 0
}
```

각 bundle hash의 canonical 원문은 같은 transaction의 별도 audit record에 보존한다. PRELOCK payload에는 다음 key를 금지한다.

- `PG05`, `PG14`, `gate_results`, `final_pair_state`
- R outcome 및 R 이후 정보
- commit 결과

### 2.3 PG05 판정 시점과 predicate

PRELOCK payload/hash를 active round transaction에 staging한 뒤, 아직 outcome loader 호출이 0인 상태에서 staged canonical bytes를 다시 읽고 검증한다.

PG05 PASS는 다음을 모두 만족할 때다.

1. `source_end_round = evaluation_round - 1`
2. `outcome_access_count_before_prelock = 0`
3. 필수 PRELOCK field와 audit bundle 원문이 모두 존재
4. 각 bundle 원문의 canonical SHA-256이 payload의 bundle hash와 일치
5. PRELOCK canonical JSON 재계산 hash가 staged prelock hash와 일치
6. staged bytes를 재파싱·재직렬화한 canonical bytes가 원본과 일치

필수 입력이나 staged record가 없으면 INCOMPLETE다. 값·hash·경계가 불일치하거나 outcome 접근이 이미 발생했으면 FAIL이다. transaction 최종 commit과 R outcome은 PG05 입력이 아니다.

## 3. PHASE 2 — FINAL-PREDICTION

### 3.1 역할

FINAL-PREDICTION은 PG05 PASS 뒤 PG01~PG13의 공식 입력·결과와 PG14가 검증할 pre-result write-set을 잠그는 layer다. PG14 자기 결과와 final PAIR state를 포함하지 않는다.

### 3.2 canonical FINAL-PREDICTION payload

```json
{
  "audit_write_set_manifest_hash": "<sha256>",
  "evaluation_round": 1,
  "gate_pg01_pg13_bundle_hash": "<sha256>",
  "outcome_access_count_before_final_prediction": 0,
  "policy_linkage_hash": "<sha256>",
  "prelock_hash": "<sha256>",
  "ranking_selection_bundle_hash": "<sha256>",
  "required_field_manifest_hash": "<sha256>",
  "schema_constraint_manifest_hash": "<sha256>",
  "source_end_round": 0,
  "write_set_version": "PAIR-FINAL-PREDICTION-1.0"
}
```

각 manifest/bundle의 canonical 원문은 같은 transaction에 함께 staging한다. FINAL-PREDICTION payload에는 다음 key를 금지한다.

- `PG14`, `pg14_result`, `final_pair_state`
- R outcome 및 R 이후 정보
- commit 결과

### 3.3 PG14 판정 시점과 predicate

FINAL-PREDICTION payload/hash와 그 canonical 원문 write-set을 staging한 뒤, outcome 접근 0 상태에서 schema/FK/constraint/hash/필수 field/persistence staging을 검증한다.

PG14 PASS는 다음을 모두 만족할 때다.

1. PRELOCK hash/link 일치 및 PG05 PASS
2. PG01~PG13 각각의 공식 입력과 PASS/FAIL/INCOMPLETE 결과가 완전
3. ranking/representative selection context와 policy linkage가 완전
4. 필수 normalized pre-result rows, report payload와 hash가 write-set manifest에 존재
5. staged schema, FK, unique/check constraint 및 canonical hash 검증 PASS
6. `outcome_access_count_before_final_prediction = 0`
7. staged FINAL-PREDICTION payload 재계산 hash 일치

필수 입력·row·manifest가 없으면 INCOMPLETE다. 값·hash·schema·FK·constraint가 불일치하거나 outcome 접근이 이미 발생했으면 FAIL이다. 실제 round commit 성공 여부는 PG14 입력이 아니다.

## 4. FINALIZATION record

### 4.1 역할

PG14 판정 후 PG01~PG14 전체 vector와 공식 precedence로 final pre-result PAIR state를 확정하고 별도 FINALIZATION record에 저장한다. FINALIZATION은 PRELOCK 또는 FINAL-PREDICTION payload/hash를 변경하지 않는다.

### 4.2 canonical FINALIZATION payload

```json
{
  "evaluation_round": 1,
  "final_pair_state": "<official PAIR state>",
  "final_prediction_hash": "<sha256>",
  "finalization_version": "PAIR-PREDICTION-FINALIZATION-1.0",
  "gate_pg01_pg14_vector_hash": "<sha256>",
  "outcome_access_count_before_finalization": 0,
  "prelock_hash": "<sha256>",
  "state_precedence_policy_hash": "<sha256>"
}
```

PG01~PG14 vector canonical 원문과 final state 판정 원자료를 함께 보존한다. FINALIZATION payload에는 outcome, future data, commit 결과를 금지한다.

## 5. 공식 round transaction 순서

```text
BEGIN ROUND TRANSACTION
1. evaluation_round R 설정
2. source_end_round = R-1 고정 및 outcome 접근 0 확인
3. candidate와 모든 pre-result 원시 입력 계산
4. rule signature 계산
5. PRELOCK canonical payload/hash 생성
6. PRELOCK과 audit 원문 staging·재검증
7. PG05 확정
8. PG01~PG13 공식 평가
9. FINAL-PREDICTION canonical payload/hash와 write-set 생성
10. FINAL-PREDICTION staging 및 schema/FK/constraint/hash/필수 field 검증
11. PG14 확정
12. PG01~PG14와 precedence로 final pre-result PAIR state 확정
13. FINALIZATION record staging·재검증
14. outcome 접근이 계속 0인지 확인
15. R outcome 최초 조회
16. outcome 저장
17. round COMPLETE staging
18. COMMIT
```

COMMIT 성공은 `ROUND_TRANSACTION_CERTIFIED`라는 실행 인증이며 연구 gate가 아니다. COMMIT 실패는 전체 rollback, round COMPLETE 아님, exposure 미반영이다. resume은 같은 R-1 prefix에서 세 canonical payload와 hash를 다시 계산하며 기존 staged 미완료 자료를 재사용하지 않는다.

## 6. 자기참조 금지와 hash 방향

```text
R-1 raw inputs
→ PRELOCK payload/hash
→ PG05
→ PG01~PG13 bundle
→ FINAL-PREDICTION payload/hash
→ PG14
→ PG01~PG14 vector + precedence
→ FINALIZATION payload/hash
→ outcome
→ commit certification
```

- PRELOCK은 PG05·PG14·final state를 참조하지 않는다.
- FINAL-PREDICTION은 PG14·final state를 참조하지 않는다.
- FINALIZATION은 앞 두 hash를 참조하지만 앞 두 payload는 FINALIZATION을 참조하지 않는다.
- outcome과 commit certification은 어느 gate/state hash의 입력도 아니다.

## 7. rollback/resume

동일 R, 동일 R-1 data prefix, 동일 rule/policy/schema version이면 PRELOCK hash, FINAL-PREDICTION hash, PG01~PG14 vector, final state, FINALIZATION hash가 동일해야 한다. 하나라도 다르면 결정론 위반으로 fail-fast한다. rollback된 round는 COMPLETE/exposure에 포함하지 않는다.

## 8. DRAFT 판정 조건

10개 timing 의미 검증이 모두 PASS할 때만 공식 PATCH로 동일 연구 의미를 승격할 수 있다.
