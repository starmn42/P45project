# P45 v2.7 워크 구현 순서

## 원칙

- v2.6 잠금 기록과 과거 결과는 수정하지 않는다.
- v2.7은 새 코드 브랜치 또는 새 버전으로 구현한다.
- 먼저 구현 감사를 하고, 그다음 코드를 수정한다.
- 50,000회 감사부터 실행하지 않는다.
- 핵심 연구 세트와 감사 인증 상태를 반드시 분리한다.

## 1단계: 파일 인식과 기준 잠금

1. `P45_v2.7_Work_UTF8_BOM_CRLF.md` 전체를 읽는다.
2. 한글 깨짐 여부를 확인한다.
3. 0장부터 42장까지 총 43개 장을 인식했는지 보고한다.
4. 파일 SHA-256을 저장한다.
5. v2.7을 신규 구현 기준으로 잠근다.
6. v2.3~v2.6 과거 기록은 읽기 전용 보존한다.

완료 보고:

- 파일 인식 PASS/FAIL
- 총 장 수
- SHA-256
- 한글 깨짐 여부
- 기존 기록 보존 여부

## 2단계: 기존 프로그램과 차이 감사

코드를 바꾸기 전에 다음을 표로 보고한다.

- 이미 구현됨
- 부분 구현
- 미구현
- 기존 규칙과 충돌
- 삭제·교체 필요
- 데이터베이스 변경 필요
- 화면 변경 필요
- 테스트 필요

특히 확인:

- 3단위 없음 여부
- 5단위가 약한 보조로 고정된 코드
- 9단위 전용 하드코딩
- 10단위와 끝수 크기 보정
- 단위 단순 점수 합산
- 감사 미완료가 HOLD를 만드는 코드
- 매회 50,000회 실행 코드
- 감사가 번호를 재선정하는 코드

## 3단계: 데이터베이스와 장부 구조

다음 테이블 또는 동등 구조를 먼저 만든다.

- unit_definition
- unit_group
- unit_round_metric
- unit_number_metric
- unit_relation
- number_ledger
- trio_ledger
- pair_ledger
- core_run
- audit_run
- audit_chunk
- sealed_forward_ledger

필수 키:

- round
- unit_type
- group_id
- engine_version
- rule_hash
- data_hash
- execution_hash

기존 잠금 기록은 마이그레이션 중 수정하지 않는다.

## 4단계: 다섯 필수 단위 계산기

아래 순서로 각각 독립 구현한다.

1. UNIT_3
2. UNIT_5
3. UNIT_9
4. UNIT_10
5. END_DIGIT

각 계산기는 다음을 반환한다.

- 그룹 정의·크기
- 통합·본번호 점유
- 점유율·기대점유
- 전멸
- 연속 전멸
- 복귀 깊이
- 정확 점유 벡터
- 조건부 번호 성과
- 전체·최근 기간
- 반대 가설
- 구조 붕괴
- UNIT 상태

UNIT_10과 END_DIGIT의 그룹 크기 보정 테스트를 먼저 통과시킨다.

## 5단계: 단위 관계 엔진

구현:

- unit_state_vector
- UNIT_CONSENSUS_SUPPORT
- UNIT_PARTIAL_SUPPORT
- UNIT_CONFLICT
- UNIT_NO_SUPPORT
- 관련근거·독립문맥근거 분리
- 파레토 지배·비지배

금지:

- PASS 개수 합산
- 단위 고정 가중치
- 숨은 종합점수

모든 충돌 원자료를 저장한다.

## 6단계: 번호 후보 엔진 연결

복귀·비복귀 번호 모두 다섯 단위 결과를 사용하도록 수정한다.

- NUMBER_PASS
- NUMBER_WEAKEN
- NUMBER_TEST
- NUMBER_HOLD
- NUMBER_FAIL

PASS 부족 시:

- PASS만 6개 이상: CORE_SET 경로
- PASS+WEAKEN+TEST 6개 이상: CORE_TEST 경로
- 6개 미만: CORE_RESEARCH_HOLD

감사 상태를 후보 생성 조건에 넣지 않는다.

## 7단계: 3개 조합·두 세트 엔진

1. 후보군의 모든 3개 조합 생성
2. 조합 unit_coverage_matrix 생성
3. 3/3을 주 통계로 계산
4. 2/3을 보조 지지로 분리
5. 조합 파레토 비교
6. 모든 비중복 조합 쌍 생성
7. PAIR_UNIT_COVERAGE_MATRIX 생성
8. 최종 쌍 공동 선정
9. 세트1·세트2 라벨 잠금

6개를 먼저 고른 뒤 나누는 기존 코드를 제거한다.

## 8단계: CORE 상태와 AUDIT 상태 분리

CORE:

- CORE_SET_READY
- CORE_TEST_SET_READY
- CORE_RESEARCH_HOLD
- CORE_SYSTEM_HOLD

AUDIT:

- AUDIT_NOT_RUN
- AUDIT_PENDING
- AUDIT_RUNNING
- AUDIT_PASS
- AUDIT_BORDERLINE
- AUDIT_FAIL
- AUDIT_INCOMPLETE
- AUDIT_INVALIDATED

감사 미완료가 CORE 상태를 HOLD로 바꾸지 않는지 테스트한다.

## 9단계: 화면 구성

같은 프로그램 안에 다음 탭을 만든다.

1. 이번 회차 핵심 연구
2. 단위별 연구
3. 감사 연구소
4. 금고

단위별 연구 탭에는 3·5·9·10단위와 끝수가 모두 보여야 한다.

감사 연구소에는 번호 변경 기능을 만들지 않는다.

## 10단계: 감사 연구소 최적화

순서:

1. 1,000회 실행
2. 캐시 저장
3. 10,000회까지 연장
4. 안정성·위약 대조
5. 형님 인증 요청 때만 50,000회까지 연장

필수:

- chunk 실행
- 중단·재개
- completed_ranges
- 병렬 작업자
- 동일 캐시 키 재사용
- 진행률
- 결과 분포 해시

매주 자동 50,000회 실행은 금지한다.

## 11단계: 필수 테스트

단위 테스트:

- UNIT_3 그룹 15개·각 3개
- UNIT_5 그룹 9개·각 5개
- UNIT_9 그룹 5개·각 9개
- UNIT_10 크기 10·10·10·10·5
- 끝수 그룹 크기 4 또는 5
- 점유율·기대점유 계산
- 전멸·복귀 깊이
- 정확 벡터
- 단위 충돌
- 파레토 비교

통합 테스트:

- 미래 데이터 차단
- 동일 입력 10회
- PASS 부족 시 TEST 세트 출력
- 감사 NOT_RUN이어도 CORE 세트 출력
- 감사 FAIL 후에도 잠긴 번호 불변
- 3/3과 2/3 분리
- 비중복 두 세트
- 과거 기록 불변

## 12단계: 성능시험

측정:

- 매회 CORE 실행 시간
- 후보 12개일 때 조합 수
- 비중복 쌍 수
- 1,000회 감사 시간
- 10,000회 감사 시간
- 캐시 적중률
- 작업자 수별 처리량
- 예상 50,000회 시간

실측 전에는 완료시간을 확정해서 보고하지 않는다.

## 13단계: 결과 비교와 승인

같은 분석 회차로 v2.6과 v2.7을 비교한다.

- 단위 결과
- 번호 후보
- 세트1·세트2
- CORE 상태
- HOLD 발생 이유
- 감사 상태
- 처리 시간

차이가 생긴 이유를 단위·관문별로 설명한다.

형님 승인 전에는 LIVE_OFFICIAL로 적용하지 않는다.
승인 다음 미분석 회차부터 v2.7 봉인 전진장부를 시작한다.
